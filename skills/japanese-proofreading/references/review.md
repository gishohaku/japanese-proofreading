# テクニカルライティング査読ルール

査読モードのときに読むファイル。校正（`checklist.md` と `rules/`）が文・語・表記の正誤を扱うのに対し、このファイルは**段落・節・文書全体の読みやすさ**を扱う。

## 目次

0. 位置づけと運用方針
1. 3C の観点 — `TW-xx`
2. パラグラフライティング — `PW-xx`
3. 文章構成の型 — `KATA-xx`
4. 提案の出し方
5. 査読例

---

## 0. 位置づけと運用方針

### 0.1 重要度は「提案」だけ

このファイルのルールに基づく指摘は、すべて重要度「提案」とする。校正ルールの「誤り」「推奨」「任意」とは区別し、出力でも別の節にまとめる。

| 重要度 | 出典 | 意味 |
|---|---|---|
| 誤り・推奨・任意 | 校正ルール | 文・語・表記の正誤や統一 |
| 提案 | 本ファイル | 読みやすさの改善候補。採否は書き手が決める |

### 0.2 提案を出す条件

提案は、**読み手がつまずく具体的な症状**があるときだけ出す。ルールに形式的に当てはまらないだけでは出さない。

つまずきの症状とは、次のようなものを指す。

- 段落を読み終えても、何を言いたい段落なのかが一言で言えない
- 前の文や段落に戻って読み返さないと意味がとれない
- 次に何が書かれるのかを予想できず、話題の切り替わりに気づけない
- 同じ説明が繰り返されていて、読む量に対して得られる情報が少ない
- 書き手が何を確定事項として述べ、何を推測として述べているのかがわからない

症状を説明できない指摘は出さない。「PREP になっていない」「トピックセンテンスがない」だけを理由にした指摘は禁止する。

### 0.3 指摘の量と優先順位

- 提案は節（見出し単位）ごとに多くても3件程度に絞る。全体を一度に直させない。
- 優先順位は「誤読のおそれ（Correct・Clear）」→「構造（パラグラフ・構成）」→「簡潔さ（Concise）」の順にする。
- 簡潔さのために明確さを損なう提案はしない（3C が衝突したら、正確、明確、簡潔の順に優先する）。

### 0.4 尊重するもの

- 書き手の文体、語り口、ユーモア、意図的な前置き
- まえがき、あとがき、コラム、エッセイ調の節。これらは基準を緩め、誤読のおそれがある箇所だけを見る
- 対話形式・物語形式で解説する書籍の構成
- 段落全体の書き換え例は、書き手が求めたときだけ出す。通常は方向性と短い例にとどめる

## 1. 3C の観点

テクニカルライティングの 3C は Correct（正確）、Clear（明確）、Concise（簡潔）を指す。読み手が内容を取り違えずに情報を受け取るための3要件である。

### 1.1 Correct（正確）

内容と表現が正確で、読み手が誤った理解をしないこと。事実そのものの正しさ（技術的な誤り）は査読の主対象ではないが、原稿の中で確かめられる矛盾（TW-C01〜C03）は、提案ではなく校正側の「要確認」として出す。

#### TW-C01 本文とコード・図表・出力の不一致

本文で述べた関数名・値・手順が、コード例・図表・実行結果と食い違っていないかを確認する。

```
本文：「この関数は配列の要素数を返します」
コード：return strlen($str);
→ 要確認：本文とコードの説明対象が一致していない可能性がある。
```

#### TW-C02 用語の一貫性

同じ概念には同じ語を使う。言い換えると、読み手は別の概念だと受け取る。

```
△ 第2章では「キャッシュ」、第3章では「一時領域」、第4章では「バッファ」と呼んでいるが、同じものを指している。
→ 提案：用語を1つに統一する。別概念なら初出で違いを定義する。
```

用語の揺れは校正ルールの表記ゆれ（GOI-01）より広い。表記が違う語だけでなく、別の語で同じものを指している場合も見る。

#### TW-C03 曖昧な数量・程度

数値で言えるものは数値で書く。

```
△ キャッシュを使うと大幅に速くなる。
○ キャッシュを使うと、手元の環境では応答時間が約120msから約15msに短縮した。
```

「大幅に」「多くの」「しばらく」「頻繁に」「重い」などが、比較や判断の根拠になっている文で指摘する。雰囲気を伝えるだけの文では指摘しない。

#### TW-C04 前提条件・適用範囲の明示

バージョン、OS、設定、対象読者の前提など、記述が成り立つ条件を明示する。

```
△ この関数は文字数を返す。
○ この関数はバイト数を返す。マルチバイト文字の文字数が必要な場合は mb_strlen() を使う。
```

条件付きでしか成り立たない内容を無条件に述べている箇所を指摘する。

#### TW-C05 断定と推量の使い分け

- 根拠のある事実は言い切る。
- 推測・経験則・未検証の内容は、そのことがわかる表現にする（「〜と考えられる」「手元の環境では〜」）。
- 断定と推量が逆になっている箇所（未検証なのに断定、仕様で決まっているのに「〜だと思います」）を指摘する。

#### TW-C06 動作主の明示

技術文書では「誰が（何が）それをするのか」が曖昧になりやすい。ユーザー、開発者、プログラム、OS、ライブラリのどれの動作かを明確にする。

```
△ 入力された値は検証されたのちに保存される。
○ フレームワークが入力値を検証し、問題がなければアプリケーションがデータベースに保存する。
```

### 1.2 Clear（明確）

読み手が一度読んで、意図どおりに理解できること。

#### TW-L01 曖昧な指示・評価語

「適切に」「うまく」「いい感じに」「必要に応じて」「ちゃんと」などは、具体的な基準を伴わないと読み手は行動できない。

```
△ 必要に応じてタイムアウトを適切に設定してください。
○ 外部 API を呼び出す場合は、タイムアウトを5秒程度に設定してください。
```

#### TW-L02 専門用語の初出定義

想定読者が知らない可能性のある用語は、初出で定義するか、定義の場所を示す。略語は初出で正式名称を併記する。

想定読者が明らかに知っている用語（入門書でない書籍の「変数」など）は指摘しない。想定読者は文書のまえがきや対象読者の記述から判断し、不明なら書き手に確認する。

#### TW-L03 抽象と具体の往復

抽象的な説明が3文以上続き、具体例・コード・図がない場合に、例の追加を提案する。逆に、例が先に来て何の例なのかがわからない場合は、先に一般論を置くよう提案する。

#### TW-L04 手順の書き方

- 手順は番号付きリストにし、1手順に1操作を書く。
- 条件分岐は手順の前に書く（「Windows の場合は、次の手順を実行する」）。
- 操作の結果（何が表示されれば成功か）を書く。

```
△ 設定ファイルを開いてポート番号を変更し、保存したらサーバーを再起動すればアクセスできるようになりますが、Windows では管理者権限が必要です。
○ 次の手順でポート番号を変更します。Windows では、管理者権限で作業してください。
  1. config.yml を開きます。
  2. port の値を 8080 に変更し、保存します。
  3. サーバーを再起動します。
  4. ブラウザーで http://localhost:8080 を開き、トップページが表示されることを確認します。
```

#### TW-L05 結論の位置

読み手が知りたいこと（結論、答え、推奨）が節や段落の最後にしかない場合、前に出すよう提案する。PW-02、KATA 各型と関連する。

#### TW-L06 読者の視点の欠落

書き手の作業の時系列（「まず〜を試した。次に〜」）で書かれていて、読み手が必要とする結果や判断基準が埋もれている場合に指摘する。調査記録として意図的に時系列で書いている場合は除く。

### 1.3 Concise（簡潔）

同じ情報を、より少ない語で伝えること。ただし明確さを損なってまで削らない。

#### TW-S01 前口上・予告の重複

```
△ ここでは、変数のスコープについて説明していきたいと思います。変数のスコープとは、変数を参照できる範囲のことです。
○ 変数のスコープとは、変数を参照できる範囲のことです。
```

見出しで話題がわかる場合、「ここでは〜について説明します」は省ける。ただし長い章の冒頭で全体像を示す予告（「本章では A、B、C の順に説明する」）は残す。

#### TW-S02 同じ内容の繰り返し

同じ説明が近い位置で言い換えて繰り返されている場合に指摘する。章末のまとめや、離れた位置での意図的な再掲は除く。

#### TW-S03 情報を持たない修飾・強調

「非常に」「とても」「本当に」「実は」「基本的に」「一般的に」などが、情報を足していない場合に削除を提案する。「基本的に」は例外があることを示す場合だけ残し、例外も書く。

#### TW-S04 名詞化・回りくどい構文

「〜の実施を行う」「〜することが可能となっている」「〜という形になる」のように、動詞で言えるものを名詞化して回りくどくなっている箇所。校正ルールの GOI-09（冗長な表現）と重なるものは校正ルール側で指摘し、ここでは段落単位で回りくどさが目立つ場合だけ扱う。

## 2. パラグラフライティング

パラグラフ（段落）を「1つの話題について1つの主張を述べる単位」として扱う書き方。3C を段落単位で実現するための手段として使う。

基本構造：

| 要素 | 役割 | 位置 |
|---|---|---|
| トピックセンテンス | その段落の話題と主張を1文で述べる | 段落の冒頭 |
| サポートセンテンス | トピックセンテンスを支える理由・具体例・データ・補足 | トピックセンテンスの後 |
| コンクルーディングセンテンス | 主張の確認、次の段落へのつなぎ（任意）| 段落の末尾 |

### PW-01 1パラグラフ1トピック

1つの段落で扱う話題は1つにする。

検出の目安：

- 段落の途中で主語・主題が別のものに切り替わり、戻ってこない
- 段落の途中に「ところで」「話は変わるが」「また、〜についても」がある
- 段落を一言で要約しようとすると「AとB」になる

```
△ PHP の文字列はバイト列として扱われる。そのため strlen() はバイト数を返す。また、PHP 8 からは JIT が導入され、数値計算の性能が向上した。マルチバイト文字を扱う場合は mb_strlen() を使う。
→ 提案：JIT の文が別の話題になっている。文字列の段落から外し、必要なら別段落にする。
```

### PW-02 トピックセンテンスを冒頭に置く

段落の最初の文で、その段落が何を言うのかを述べる。

検出の目安：

- 段落の冒頭が背景・経緯・前置きで、主張が末尾にある（起承転結型）
- 冒頭の文が抽象的すぎて、段落の内容を予告していない（「次に、もう1つの点について考える」）

```
△ 以前はすべてのリクエストでデータベースに問い合わせていた。アクセスが増えると応答が遅くなり、障害も起きた。調査の結果、同じクエリが繰り返し実行されていた。そこで、結果をキャッシュすることにした。
○ 同じクエリの結果はキャッシュすることにした。以前はすべてのリクエストでデータベースに問い合わせており、アクセスが増えると応答が遅くなって障害も起きていた。調査すると、同じクエリが繰り返し実行されていた。
```

例外（指摘しない）：

- 章や節の導入段落で、読み手の関心を引くために問いや事例から始める場合
- 結論に至る過程そのものを読ませる意図がある解説（デバッグの過程を追う節など）
- 段落が1〜2文と短く、冒頭の文がそのまま話題を示している場合

### PW-03 サポートセンテンスはトピックを支えるものだけ

トピックセンテンス以外の文は、理由・根拠・具体例・データ・条件・補足のいずれかとして、トピックセンテンスを支える。どれにも当たらない文は、別段落に移すか削除を提案する。

サポートセンテンスの並べ方：

- 理由 → 具体例、の順にする
- 重要なものから先に書く
- 「第一に」「次に」などで数を示すと、読み手は全体量を予測できる

### PW-04 文と文の接続（接続詞）

文と文の論理関係を、接続詞（または接続の働きをする表現）で明示する。

| 論理関係 | 主な接続詞 | 使う場面 |
|---|---|---|
| 順接（因果）| そのため、したがって、その結果 | 前の文が原因・理由、後の文が結果 |
| 理由 | なぜなら〜からだ | 後の文が前の文の理由 |
| 逆接 | しかし、ところが、それでも | 前の文から予想されることと反対 |
| 対比 | 一方、それに対して | 2つのものを比べる |
| 添加 | さらに、加えて | 同じ方向の情報を足す |
| 並列 | また、同様に | 同じ重みの情報を並べる |
| 換言 | つまり、すなわち、言い換えると | 同じ内容を別の言葉で述べる |
| 例示 | たとえば | 具体例を示す |
| 補足 | なお、ただし | 例外・注意を加える |
| 転換 | では、次に、ところで | 話題を変える（段落の切れ目で使う）|
| 結論 | このように、以上から | まとめる |

検出の目安：

- **関係の誤り**：接続詞が示す関係と、実際の文の関係が合わない（因果関係がないのに「そのため」、反対の内容でないのに「しかし」）。
- **関係の欠落**：2文の関係が読み取れず、読み手が推測しなければならない。特に逆接と因果の欠落は誤読につながる。
- **過剰**：すべての文に接続詞が付いていて、かえって重要な関係が埋もれている。
- **「また」の多用**：並列でない関係（添加・転換・因果）を「また」でつないでいる。
- **段落内の転換**：「ところで」「では」などの転換の接続詞が段落の途中にある（PW-01 の兆候）。

```
△ この方式はメモリ使用量が少ない。また、大きなファイルは扱えない。
○ この方式はメモリ使用量が少ない。ただし、大きなファイルは扱えない。
```

校正ルールの JOSHI-01（接続助詞「が」）、JOSHI-09（同じ接続詞の連続）と併せて見る。

### PW-05 段落の長さ

目安は2〜6文、または200〜400字程度。

- 8文以上ある段落は、話題が複数ないか（PW-01）を確認し、分割を提案する。
- 1文だけの段落が3つ以上連続する場合（ブログ調の改行）、論理的なまとまりごとに統合を提案する。ただし Web 記事で意図的に短くしている場合は【任意】の扱いにとどめる。
- 箇条書き・コード・図表の前後の短い段落は対象外。

### PW-06 段落の順序

段落は、読み手が理解しやすい順に並べる。

- 既知から未知へ（読み手が知っていることから始める）
- 一般から具体へ（全体像 → 詳細）
- 時系列順（手順、歴史的経緯）
- 重要度順（重要なものから）

節の中で段落の順序が入れ替わっていて、前の段落の理解に後の段落の内容が必要になっている場合に提案する。

### PW-07 拾い読みテスト

各段落の最初の文（トピックセンテンス）だけを順に抜き出して読み、節の内容と流れが理解できるかを確認する。スキルが節全体を評価するときの主要な手順とする。

- 拾い読みで流れが通れば、段落構造は良好とみなし、PW 系の提案は原則出さない。
- 通らない箇所があれば、その段落について PW-01〜04 のどれが原因かを特定して提案する。

### PW-08 見出しと内容の一致

- 見出しが示す内容と、節の本文が一致しているか。
- 見出しの直後に、その節で何を述べるかを示す導入（1〜2文）があるか。見出しの直後がいきなりコードや細部から始まる場合に提案する。
- 見出しの粒度・表現（体言止めか文か、「〜とは」「〜する方法」など）が同じ階層で揃っているか【任意】。

## 3. 文章構成の型

節・項・長めの段落群の構成を評価するための型。型に当てはめること自体は目的ではない。節の目的に対して要素が欠けているときに、その要素を補う提案に使う。

### 3.1 型の一覧

#### KATA-01 PREP（Point → Reason → Example → Point）

| 要素 | 内容 |
|---|---|
| Point | 主張・結論 |
| Reason | その理由 |
| Example | 具体例・根拠・データ |
| Point | 主張の再確認 |

向いている節：設計判断の説明（なぜ A を採用したか）、推奨・ベストプラクティス、比較の結論、意見を述べるコラム。

検出の目安：主張があるのに理由がない、理由はあるが具体例がない、結論が最後まで出てこない。

#### KATA-02 SDS（Summary → Details → Summary）

| 要素 | 内容 |
|---|---|
| Summary | 全体の要約（これから何を述べるか）|
| Details | 詳細 |
| Summary | まとめ（何を述べたか）|

向いている節：章・節の導入とまとめ、機能や仕組みの紹介、調査・作業の報告、長い解説。

検出の目安：長い節に導入の要約がなく、読み手が全体像を持たずに詳細を読まされる。節の終わりで何が重要だったのかがわからない。短い節では最後の Summary を省いてよい。

#### KATA-03 DESC（Describe → Express → Specify → Choose）

| 要素 | 内容 |
|---|---|
| Describe | 状況・事実を客観的に描写する |
| Express | その状況による影響・問題・懸念を述べる |
| Specify | 具体的な解決策・提案を示す |
| Choose | 提案を採った場合・採らなかった場合の結果、または選択肢を示す |

向いている節：問題提起と解決策、アンチパターンとその対処、トラブルシューティング、移行・変更の提案、レビューコメント。

検出の目安：事実と感想が混ざっている（Describe と Express の混在）、問題を述べたまま解決策がない、解決策の効果や代替案が示されていない。

#### KATA-04 手順型（目的 → 前提 → 手順 → 確認）

| 要素 | 内容 |
|---|---|
| 目的 | この手順で何ができるようになるか |
| 前提 | 必要な環境、事前に済ませておくこと |
| 手順 | 番号付きの操作（TW-L04）|
| 確認 | 成功したことの確かめ方、失敗した場合の対処 |

向いている節：インストール、環境構築、ハンズオン、操作説明。

検出の目安：前提が手順の途中で後出しされる、成功の確認方法がない。

#### KATA-05 概念説明型（定義 → 具体例 → 仕組み → 注意点）

| 要素 | 内容 |
|---|---|
| 定義 | それが何かを1〜2文で述べる |
| 具体例 | 最小のコード例や身近な例 |
| 仕組み | なぜそう動くのか、内部でどう処理されるか |
| 注意点 | 落とし穴、例外、関連する概念との違い |

向いている節：用語・概念・関数・データ構造の解説。

検出の目安：定義がないまま仕組みの説明に入る、仕組みだけで具体例がない。

### 3.2 型の選び方

スキルは節ごとに、まず**節の目的**を判定し、それに合う型と比べて欠けている要素だけを提案する。

| 節の目的 | 第一候補 | 第二候補 |
|---|---|---|
| 主張・判断・推奨を伝える | PREP | DESC |
| 全体像を示す・報告する | SDS | — |
| 問題と解決を示す | DESC | PREP |
| 操作を教える | 手順型 | SDS |
| 概念を教える | 概念説明型 | SDS |

- 書き手がすでに別の型で筋の通った構成をしている場合、型の変更は提案しない。
- 1つの節に複数の型が入れ子になってよい（SDS の Details の中に PREP の段落がある、など）。
- 提案では型の名前を出してよいが、型の名前だけでなく「何が欠けていて、読み手がどう困るか」を書く。

## 4. 提案の出し方

### 4.1 判定の手順

1. 文書の種類と想定読者を把握する（まえがき、対象読者の記述、文体から）。
2. 節（見出し）ごとに、節の目的を判定する（3.2）。
3. 拾い読みテスト（PW-07）で段落構造を確認する。
4. 流れが通らない箇所、つまずきの症状（0.2）がある箇所について、原因となるルールを特定する。
5. 3C の観点（TW）で、誤読のおそれがある箇所を確認する。
6. 優先順位（0.3）に従い、節ごとに多くても3件程度に絞って提案する。

### 4.2 出力の形式

提案は校正の指摘（誤り・推奨・任意）とは別の節にまとめる。1件ごとに次の項目を書く。

```
【提案】<節の見出し> 第<n>段落
観点：<ルールID>（<観点名>）
気になった点：<読み手の立場で、どこでどうつまずくか>
提案：<改善の方向性>
例：<必要な場合だけ、短い書き換え例>
```

例：

```
【提案】3.2 キャッシュの導入 第1段落
観点：PW-02（トピックセンテンス）、KATA-01（PREP）
気になった点：段落の結論「結果をキャッシュすることにした」が最後の文にあり、それまでの3文が何のための説明なのかがわからないまま読むことになる。
提案：キャッシュを導入した判断を冒頭で述べ、その後に経緯（理由）を続ける。
例：「同じクエリの結果はキャッシュすることにした。以前は〜」
```

### 4.3 書き方の注意

- 「〜すべき」「〜が間違っている」ではなく、「〜すると読みやすくなる」「〜と読まれるおそれがある」のように書く。
- 指摘の根拠は、ルール名ではなく読み手の体験（どこで迷うか）で説明する。
- 書き換え例は元の文の内容・語彙をできるだけ保ち、新しい情報を足さない。情報が足りないために書き換えられない場合は、何を補えばよいかを書き手に尋ねる形にする。
- 文書全体に共通する傾向（全節で結論が末尾にある、など）は、個別に繰り返さず、冒頭で1件の総評としてまとめる。

## 5. 査読例

### 修正前

> ### 4.1 セッションの保存先
>
> PHP のセッションはデフォルトではファイルに保存されます。また、Redis に保存することもできます。サーバーが1台のうちは問題ありませんが、サーバーを複数台にしたとき、ロードバランサーがリクエストを別のサーバーに振り分けると、そのサーバーにはセッションファイルがないのでログイン状態が失われてしまいます。なお、PHP 8.3 では型付きクラス定数が追加されました。そのため、複数台構成ではセッションを Redis などの共有ストレージに保存するのが一般的です。

### 提案

```
【提案】4.1 セッションの保存先 第1段落
観点：PW-01（1パラグラフ1トピック）
気になった点：「PHP 8.3 では型付きクラス定数が追加されました」はセッションの話題と関係がなく、ここで読み手の理解が途切れる。
提案：この文を削除するか、該当する別の節に移す。

【提案】4.1 セッションの保存先 第1段落
観点：PW-04（文の接続）、PW-02（トピックセンテンス）
気になった点：「また、Redis に保存することもできます」が冒頭近くにあるが、なぜ Redis が出てくるのかは最後まで読まないとわからない。さらに、上記の文を削除すると「そのため」が直前の文（ログイン状態が失われる）を受けることになるが、間に関係のない文があると因果関係が読み取りにくい。
提案：結論（複数台構成では共有ストレージに保存する）を冒頭に置き、理由（ログイン状態が失われる）を続ける。
例：「サーバーを複数台で運用する場合は、セッションを Redis などの共有ストレージに保存します。PHP のセッションはデフォルトではファイルに保存されるため、〜」
```

### 修正後の一例（書き手が書き換え例を求めた場合）

> ### 4.1 セッションの保存先
>
> サーバーを複数台で運用する場合は、セッションを Redis などの共有ストレージに保存します。PHP のセッションは、デフォルトではサーバー上のファイルに保存されます。そのため、ロードバランサーがリクエストを別のサーバーに振り分けると、振り分け先にはセッションファイルがなく、ログイン状態が失われます。サーバーが1台であれば、デフォルトのファイル保存で問題ありません。
